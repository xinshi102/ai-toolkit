# Windows：有限主控额度下的协作

此模式接在现有 `workflow.py` 上。执行者自行实现、测试、修复；本地程序等待并回收；只在必要执行前审查、交付验收或真实阻塞时派发主控。不是每个工具动作、每个阶段都调用主控。

主控负责生成工作图，用户无需写 JSON 或维护多个聊天窗口。普通单对话任务仍直接完成。

## 优先选择执行闭环，按需选择本模式


简单任务可由一个有能力的充足渠道执行者完成并提供客观检查。需要独立复核时，在原工作图里安排独立验证节点，由其检查原始需求与实际产物；不配置 `supervision`，就没有隐含的 GPT 终审。普通修复、测试和等待在授权工作包内完成，真实能力缺口或证据冲突才升级；重要歧义与新权限由用户决定。不要固定走 DSH→GPT 或让模型付费轮询。用户直接在 DSH 请求 Codex 建议时，DSH 仍是主控，不算绕过流程。

文件节点用实际文件、哈希及必要测试作验收，避免无业务用途的 `final_json_values: {implemented:true}` 证明。确需 JSON 交接时保留严格格式；若执行者格式失败但产物经独立验证可用，显式修订验收/以已验证 external 输入接续，原失败保留在 history，不能清洗成原尝试通过。无证据时不得采用这种接收。


## 工作图配置

在原有 nodes 旁加入：

```json
"supervision": {
  "goal": "本次交付的完整目标",
  "constraints": ["不得超出原权限与声明的文件范围"],
  "acceptance": ["明确可检查的验收标准"],
  "provider": "codex",
  "max_calls": 8,
  "window_seconds": 18000,
  "token_limit": 120000,
  "reserve_tokens": 16000,
  "max_workflow_calls": 4,
  "max_repairs": 1,
  "timeout_seconds": 240,
  "final_checks": [{"kind":"python_unittest", "module":"test_example", "timeout_seconds":60}]
}
```


- 默认低风险阶段无需 Gate1；需要时给节点加 `requires_gate1: true`，或配置 `gate1: true` 对全图启用。
- 阶段已有显式检查通过后才释放依赖。各执行者全部完成、整体验证通过后，一次 Gate2；通过才将整个流程标记 accepted。
- 审查使用真实约束、验收标准、阶段摘要、文件路径、检查回执；不注入完整对话。允许只读下钻实际产物，不以执行者摘要自证。
- 快照超过 16 KiB 时停止并要求拆分工作包，不静默删除约束。
- 审查 FAIL 可返回 `fixes: [{"node":"已有节点ID","instruction":"具体修复"}]`。只在既定范围重做该节点与后继，保留旧尝试；超过 max_repairs 或需要新权限则 needs_attention。
- 执行者遇到真实歧义返回 JSON `{"status":"needs_decision","reason":"..."}`；即使机械检查碰巧通过，也不会当作已交付。
- 取消和 unknown 沿用现有资源锁规则，不能把 ACP 取消回执当作工具停止证明。

## 运行和接续

沿用 `init MANIFEST`。`run --max-concurrency 2 --compact` 一次执行到交付或需要决定，无模型状态轮询。`start --max-concurrency 2` 将本地调度程序隐藏启动，日志在流程目录 scheduler.log。`summary` 输出小摘要；`usage` 输出共享账本汇总。

每条命令使用原有 `--project-root` 与项目内 `--state`。执行者不修改 workflow.json；正常阶段结果、版本、修复、审查回执都保存于该文件。`collab.sqlite` 是去重通知记录；没有第二份可编辑 Plan。

`start` 使用 `serve` 后台模式：若账本给出明确的本地窗口恢复时间，程序定时等待后自动重新准入，不需要模型轮询。每流程上限、未知调用或不知道真实账户何时恢复时不猜测时间、不循环试调用，保留暂停状态。桌面退出持续运行仍需单独验收。

需要修订需求仍用 `revise`，显式 expected_revision；修改影响到的节点重新执行。已批准且未受影响的分支保留。恢复时按稳定事件键和队列回执续接，不重复派发已发出的审查。

本地调度仍通过轻量 SQLite 状态检查等待子进程，**不调用模型**。这是模型调用按事件发生，不是宣称底层完全没有轮询。`start` 不安装系统服务，也不证明桌面退出后持续运行；不自动唤醒当前聊天 UI。后台 CLI 审查回执保存在流程中，当前聊天可接续读取。

## 预算与用量

共享账本为安装项目 `.work/controller-usage.sqlite`，各工作流共同计数，不能通过另开工作流重置；不得上传。SQLite 事务先保留调用名额，再派发。五小时滚动窗口是本地策略，真实订阅窗口可能不同。

- 到上限不再派发主控，流程为 awaiting_controller，已授权的其他执行者仍可完成。保留任务与产物，恢复运行时重新判断准入。
- 单次调用开始前按 reserve_tokens 预留；实际用量回收后核算。它不能硬限制后台模型单次实际 token，也不能预测账户剩余额度。
- 每流程调用数也有限；这不是五小时后自动重置的每流程上限。
- 只有真实已报告的输入、缓存读取、输出才记为已知；缺失用量保留预留额，不伪造零。缓存写入包含在总输入中，不算缓存读取。
- 无法确认是否已派发的崩溃，或 unknown，会保留名额，不自动重试。人工核对队列/日志后，才通过带真实用量的 `controller_usage.finish` 解除不确定计量；不得凭空填零。
- 已完成且计量明确的调用随本地窗口过期释放；未知计量不靠等待自动清零。
- 报表区分 controller/executor/provider；运行器不能读取或推算当前桌面聊天的隐藏消耗，不能将原始 token 直接换算为订阅配额或宣称整体节省百分比。
- 渠道是否「稀缺」按用户实际账号/订阅条件判断，不是模型能力排名；本模式不假定某渠道底层模型，也不预设哪个渠道固定充足或固定稀缺。评估是否省额度/费用时，须拿同类任务的旧流程按相同验收标准对照实际调用，不能用各渠道未加权 token 总数或未实测的「净节省」当结论，详见 `outputs/2026-10-21-weighted-cost-review/`。

`events.py`、`gate.py`、`state.py`、`budget.py` 旧独立实验接口保留兼容。本模式使用 `supervision.py` 和共享 `controller_usage.py`，不是再启一个 gate.py 模型轮询程序；不要同时让独立 gate 消费本模式事件库。
