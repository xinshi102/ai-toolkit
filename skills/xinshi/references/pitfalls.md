# 场景坑点（按需读）

旧版正文里的“不…不…”规则都是真实踩过的坑，按场景搬到这里。只在命中对应场景时读那一节，普通任务不用读。来源：3.0.0-trial.6 正文（备份在 `archive/2026-10-26-pre-slim/xinshi/`）。

## 部署 / 生产数据
- 部署前先备份，并准备好回滚脚本；回滚要覆盖所有被改的服务，不能只恢复其中一个。
- 重启服务要沿用原进程的环境变量（含 token），不要用 `run.sh` 之类的裸启动脚本；不要打印 env 原文。
- 生产 apply、迁移、重算前先在副本上 dry-run，并让用户确认影响范围和回滚点。
- 幂等：已经是目标状态就跳过，不要重复写入或重启。
- 换行符：Windows 上编辑 LF 文件时保持 LF，避免整份文件被改脏。

## 进程与资源
- 只停能证明属于本任务的进程；停不掉或无法确认时记为 UNKNOWN 并保留资源锁，不要当作已清理，也不要直接重派。
- 工作树不隔离端口、数据库、Unity/Excel 等桌面实例：要么独占时段，要么另开实例。
- 同一文件同一时间只能有一个执行者在写；发现不认识的修改，先查归属，不替别人回退。

## 权限与渠道
- 访问被明确拒绝时，先核对授权边界；不要换另一个渠道的管理员身份去绕过。
- 修复不扩大原有授权；能力选择不能扩大权限。
- 工具返回 “blocked by policy” 时，如实转告用户，不要猜是哪条策略。
- 征询另一个渠道的意见不转移主控权；任务的主控仍留在用户发起任务的宿主。

## 宿主自升级
- 升级插件/版本、修改宿主配置或技能安装时，执行者不能是被改的那个宿主；监督者也要能在该宿主失效后继续工作。

## Windows 桌面 / Unity
- Unity 菜单的 WM_COMMAND id 会随菜单重建而变化，每次要按路径重新解析，或者用 `ExecuteMenuItem` 字符串（2026-10-20 事件）。
- 能用 CLI 就不用桌面自动化（2026-10-19 用户纠正）。

## 界面类任务（看板、页面、可视化）
- 用户说“不好看 / 可视化不行”时，先确认这个界面要回答哪几个问题、按什么优先级，再从零排版；不要在旧框架上加减（2026-10-27 看板改版，用户评价“做了不如不做”）。
- “换布局”和“换视觉语言”（配色、元素、字体层级、密度）是两件事。交付时分别说明各做了没有，不要把重写代码说成重做设计。
- 用户提到“调研”时，要真的查成熟产品和设计资料，先交调研结论和几种风格方向的静态样张让用户挑，确定方向后再写正式代码；不要把自己的审美说成调研结果。
- 布局验收用 DOM 实测元素的坐标、尺寸和溢出；AI 看图只用来判断美观，并且要等数据加载完再截图，否则会误判为空白页。
- 本地样张/页面挂到本地 HTTP 服务上打开，不要用 `file://`（部分宿主的内嵌浏览器打不开，会白跑一轮截图）。
- 页面脚本包进 IIFE，或避开 `top`、`name`、`status`、`parent` 这类浏览器全局名；重名会导致整页空白（2026-10-27 方向 3 样张）。
- 截图前先读一次浏览器控制台报错，并用 DOM 确认数据已渲染（元素数量 > 0），再交给 AI 看图。
- 控制台日志可能是之前打开的页面残留的：先确认报错属于当前页面（看报错里的地址，或者新开页面后再读），再去查源码（2026-10-27 正式版误查 `top` 重名）。
- 页面改完出现异常（卡在加载中、空白），先回读刚改的几行源码，确认改动真的写进了文件，再查接口和数据；工具报告“替换成功”不代表每一处都改了（2026-10-27 7 天隐藏常量漏写，先绕去查了接口速度）。
- 点击后才加载的接口（详情抽屉、展开项）要单独测响应时间，不能只看首屏正常；超过 1 秒先查是否每次都在全量重算（2026-10-27 详情接口每次重新解析全部记录，耗时 4 秒）。
- 用户的抱怨只是线索，不等于需求。改动会影响到汇报频率、要不要证据、什么时候停之类的方面时，先问清用户偏好再动手（2026-10-26 秘书模式讨论）。

## Windows 写文件
- 写入内容含中文、引号或多行时，先写成 `.py`/`.json` 文件再执行，不要把长字符串直接塞进 PowerShell 命令。
- 找配置文件时先列出各宿主已知的配置路径，不要对整个用户目录做递归内容搜索（会跑几分钟没结果）。

## 跨渠道成本对比
- 要说“省了额度/费用”，必须拿同类任务的旧流程按相同验收标准做对照；不能拿各渠道未加权的 token 总数下结论。参考 `outputs/2026-10-21-weighted-cost-review/`。
- 渠道贵不贵按用户实际账号额度判断，不按模型能力排名。

## 验收的思维陷阱
- 检查通过只证明它检查的那件事；多方意见一致也不等于验证通过。
- 独立复核的顺序：先读需求和验收标准，再看产物，最后才看执行者的说明。
- 执行者自报完成、文件存在都不算通过；要看真实产物。

## 2026-10-26 复盘（GPT 主控 + 执行渠道 A）
- 主控用 40–45 秒的 sleep 循环加读日志等执行者：一共 216 次，每次醒来都重新读一遍整个上下文，单轮输入 5,000 万–6,000 万 token。→ 改为阻塞等待。
- 每个包限 ≤2500 字、≤20 轮：90 个包里有 22 个因轮数耗尽而失败，约 39% 的工具调用花在读代码上（每个新包都要重新读一遍）。→ 改为按里程碑派包、轮数给够。
- 主控逐包亲自复跑验收，GPT 额度多次耗尽。→ 改为 L1/L2/L3 分级验收。
- 验证措辞写进了知识库正文，用户评价“根因和解决方案就是一坨”。→ 交付物和验收记录分开。
