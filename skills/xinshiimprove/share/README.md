# share —— 跨项目、跨工具的 AI 协作基础库

版本：v1.13
更新日期：2026-10-10

> ⚠️ **本文件是给人看的入口说明。AI 日常不读本文件** —— AI 的唯一常驻索引是 `ROUTER.md`。
> 导航细节（路由表、协议分节、文件地图）以 `ROUTER.md` 为准，本文件不重复。

---

## 这是什么

一套**跨项目、跨 AI 工具、可长期维护**的协作规则库。三个目标：

1. **标准**：每个项目、每个工具，AI 的工作方式一致
2. **可沉淀**：真实任务中的经验能被提取成通用技能
3. **可自进化**：规则自身能被观察、试验、修改、清理，且全程有据可查

`share/` 是**只读基础库**。默认不得写入；仅当人类当次显式下令时才可修改，
且必须同步更新 `CHANGELOG.md` 与被改文件版本号。

## 怎么开始

| 我要做什么 | 对 AI 说 |
|---|---|
| **新建项目 / 初始化环境**（全新） | 读 `<SHARE_ROOT>/new_project.md`，初始化环境 |
| 已有项目接入 | 读 `<SHARE_ROOT>/adopt_project.md`，把这个项目接入协议 |
| 旧对话标准化 | 读 `<SHARE_ROOT>/standardize_legacy.md`，把这段旧对话标准化 |
| 日常开工 | 先读**项目目录下的** `AGENTS.md`，再按其中「必须先读」读 `ROUTER.md` |

⚠️ `share/` 里**没有** `AGENTS.md`，只有它的模板。
真正的 `AGENTS.md` 在**你的项目目录**里，由模板生成。
（同理：`progress_template.md` 在 share，`progress.md` 在项目。）

**完整的场景→文件路由表在 `ROUTER.md`。**

## 目录结构（按层）

| 层 | 文件 | 职责 | 可变性 |
|---|---|---|---|
| **索引** | `ROUTER.md` | AI 唯一常驻：红线 + 路由表 + 协议分节指引 | 随内容同步 |
| **L0 宪法** | `collaboration.md` §裁决优先级、§share 写权限；`governance.md` §元规则、§规则演进闭环 | 所有规则的地基 | **锁定** |
| **L1 协议** | `collaboration.md` 其余章节 | 工具无关、项目无关的协作规则 | 严格（五道闸） |
| **L2 流程** | `_project_common.md`、`new_project.md`、`adopt_project.md`、`standardize_legacy.md`、`new_skill.md`、`new_tool.md`、`distill.md`、`governance.md` | 各类任务怎么走 | 中等 |
| **L3 模板** | `agents_template.md`、`project_files_template.md`、`task_card_template.md`、`progress_template.md`、`skill_template.md` | 项目文件长什么样 | 宽松 |
| **L4 技能** | `skills/*.md` | 通用领域方法与避坑经验 | 宽松 |
| **L5 工具** | `tools/*.md` | 各 AI 工具的差异与降级方案 | 宽松 |
| **台账** | `observations.md`、`proposals.md`、`CHANGELOG.md` + 各自 `_archive` | 证据与历史 | 只追加 |
| **L6 项目** | 各项目目录（不在 share 内） | 项目专属的一切 | 自由 |

**向下解决原则**：改动需求出现时，能在低层解决就不许动高层。详见 `governance.md` §规则分层与可变性。

### 全新项目：先骨架，后长成

环境初始化**只问 4 个问题**（项目名 / 根目录 / share 路径 / 一句话描述，最后一项可跳过），
立刻建出骨架；目标、约束、环境、不可逆操作等**在你后续提需求的过程中逐步补上**。

补足规则见 `agents_template.md` §渐进补足规则。三条最关键的：

| 触发 | 动作 |
|---|---|
| 你首次提需求 | AI 提炼「项目目标」，复述确认后写入 |
| 你说"别动 X" | 追加到「项目特有约束」，注明来源与日期 |
| AI 识别出不可逆操作 | 追加到清单 + **当场停下**提议升干预档 |

⚠️ 骨架里的不可逆操作写的是 `（暂无，⚠️ 未确认）`——这是"还不知道"，**不是"确认没有"**。
在你明确确认之前，干预档不得降到 A。

## 规则怎么改（六环闭环）

```
观察 → 分析 → 提案 → 试验 → 固化 → 清理
 ①      ②      ③      ④      ⑤      ⑥
AI反问  AI+人   AI写   项目内  AI执行  AI查重
        判断   人选   人判断  人确认  人决定
```

| 环节 | AI 做 | 人类做 |
|---|---|---|
| 观察记录 | 每次任务结束**反问**四问（一句话） | 认下哪条；确认草稿后才入台账 |
| 提案 | 分析观察，写提案 | **选哪个提案试验** |
| 试验 | 在项目内执行新规则，报告现象 | **判断是否有效** |
| 固化 | 写入 share + 记 CHANGELOG | **确认改什么、删什么** |
| 清理查重 | 新对话中独立审查，出待删名单 | **决定删什么、合什么** |
| 版本管理 | 更新版本号和日期 | **设定下次审查日期** |

**不得跳步**：没有观察记录不许提案，没有试验不许固化（仅纯编辑性与删除类改动豁免试验）。

完整定义见 `governance.md` §规则演进闭环。

## 元规则速查（一条规则该不该存在）

| # | 规则 |
|---|---|
| M1 | 没有这条规则 AI 也能做对的 → 不要写 |
| M2 | 不能被事实执行和验收的 → 不要写 |
| M3 | 写了之后从未被触发的 → 要删（灾难防御类豁免，须标注） |
| M4 | 各层有行数上限，超限先删再加 |
| M5 | 一条规则（或一份模板）只能有一个出处 |
| M6 | 改动必须可追溯到观察与提案 |
| M7 | 通用层（L0~L3、索引）不得出现项目专有名词 |

完整定义与豁免情形见 `governance.md` §元规则。

| 工具 | 关键缺口 |
|---|---|
| Codex | 截图不保证可用、网络可能被禁 |
