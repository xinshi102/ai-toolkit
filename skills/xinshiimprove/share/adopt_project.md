# 存量项目接入协议

> **触发场景**：已在跑的项目要接入协议｜**不用读的情况**：从零新建（读 new_project.md）｜**行数**：151

版本：v1.3
更新日期：2026-09-21
上位文件：`collaboration.md`
公共部分：`_project_common.md`（入口三选一 / 档位 / 方案确认门 / 接线模板 / 公共验收项 / 公共知识沉淀 / 公共边界）

当人类要求把一个**已经在跑的项目**接入本套协议时，按本协议执行。
本文件只写**本流程差异**，公共部分不重复。

## 核心原则：接线，不动结构

存量项目通常已有自己的文件组织、正在运行的脚本、硬编码的路径。
**协议向项目让步，不是项目向协议让步。**

- 不改名、不搬目录、不重构已有文件
- 通过**映射表**声明"项目的 X 就是协议的 Y"
- 结构差异一律走 `collaboration.md` §裁决优先级 的**显式声明偏离**机制，不默默凑合
- 只补真正缺失且有价值的文件

违反本原则的典型错误：为了让目录名对上模板，去改一个正在每天定时运行的系统的路径。

---

## 第 1 步：清点现状

**只读**，不写任何文件。产出一份清单：

1. 项目根目录下所有文件与目录（含行数、最后修改时间）
2. 哪个文件是当前工具的自动加载入口（如 `AGENTS.md` / `CLAUDE.md`）
3. 现有文件各自承担什么职责（读其开头与小节标题判断）
4. 是否已有正在运行的东西（定时任务、服务、脚本），及其依赖的路径
5. 是否已存在自发形成的规则（工作规则、约定、不做清单）

---

## 第 2 步：建映射表

把项目现有文件映射到协议概念。产出下表，缺失项留空：

| 协议概念 | 项目中的对应物 | 说明 |
|---|---|---|
| `AGENTS.md`（项目上下文） | | |
| `knowledge_base.md`（系统是怎样的） | | |
| `progress.md`（这件事做到哪了） | | |
| 任务卡 `tasks/<名>.md` | | |
| `acceptance/`（验收脚本/清单） | | |
| `logs/`（现场证据） | | |
| `output/`（运行结果） | | |
| `pending_question.md` | | |
| 引用的通用技能 | | |

映射规则：

- 职责一致即可映射，**不要求同名**（`PROGRESS.md` 可映射为 `progress.md`）
- 一个项目文件可同时承担多个协议角色，在说明里写清
- 确实没有的，记为缺失，进入第 4 步判断要不要补

---

## 第 3 步：识别冲突

逐条比对，列出项目现状与 `collaboration.md` 冲突之处。常见类型：

| 冲突类型 | 例子 |
|---|---|
| 职责混写 | "待验证"清单写在知识库里，但协议规定它属进度 |
| 命名不同 | 进度文件用大写文件名 vs 协议模板的小写 |
| 位置不同 | 任务卡在根目录 vs 协议要求 `tasks/` |
| 缺少环节 | 无 `pending_question.md`，一直靠对话直接问 |
| 规则重复 | 项目自定规则与协议某条等价但措辞不同 |
| **内容重复** | 同一事实在两个文件里各记一份（如项目上下文与知识库都记系统状态）→ 违反 `governance.md` M5 |

**内容重复的检查方法**：抽取映射表中职责相邻的两个文件（如项目上下文 vs 知识库），
对关键词做交叉计数；两边命中数都显著 > 0 的，逐条确认是否同一事实。

对每条冲突，给出处置建议（三选一）：

- **协议让步** → 在 `AGENTS.md` 中显式声明偏离（命名、位置类冲突基本都选这个）
- **项目补齐** → 补文件或调整内容（缺少环节类，且补的成本低）
- **待人类裁决** → 两边都有道理，或改动有风险

内容重复类冲突**一律为"待人类裁决"**——判断哪份是单一事实来源需要业务知识。

**不得自行决定"协议让步"以外的任何改动**，第 4 步前必须等人类确认。

---

## 第 4 步：输出接入方案，等确认

按 `_project_common.md` §方案确认门 输出，并额外附：

1. 第 1 步的现状清单
2. 第 2 步的映射表
3. 第 3 步的冲突清单 + 处置建议（含内容重复项）
4. 是否发现值得沉淀为通用技能的内容（见 `new_skill.md`）

---

## 第 5 步：接线

确认后执行。接线节的完整模板见 `_project_common.md` §接线，本流程不重复。

要点：

- 接线动作**只在入口文件顶部插入一节**，不改该节以外的任何内容
- 「文件映射」表按第 2 步结果填写
- 「声明偏离」按第 3 步中判为"协议让步"的冲突逐条填写
- 然后补齐第 4 步确认过的缺失文件

**本流程额外边界**（公共边界见 `_project_common.md` §公共边界）：

- 不修改入口文件的其他章节内容
- 不修改任何正在被运行中的脚本引用的路径
- 不删除任何现有内容（包括看起来重复的）——重复项只标记，由人类裁决

---

## 第 6 步：验收

接入产物为**文档产物**，走 checklist 路径。
先逐条核对 `_project_common.md` §公共验收项，再核对本流程专有项：

```markdown
# 存量项目接入专有验收项

- [ ] 第 3 步识别出的每条冲突，都在「声明偏离」中有对应条目，或已被补齐
- [ ] 未改名、未移动、未删除任何原有文件（以接入前的文件清单比对为证）
- [ ] 未修改入口文件中「协作协议」节以外的任何内容
- [ ] 正在运行的定时任务/服务未受影响（列出其配置或状态为证）
- [ ] 内容重复已处理：项目原有文件与协议概念文件之间无同一事实的两份记录（M5）
```

按 `collaboration.md` §自评报告格式 输出报告，等人类确认。

---

## 第 7 步：知识沉淀

按 `_project_common.md` §公共知识沉淀 执行。

## 边界

除 `_project_common.md` §公共边界 外，本流程额外遵守：

- 不为对齐协议命名而改动存量文件
- 不删除项目中看似冗余的内容——它可能有你不知道的用途
