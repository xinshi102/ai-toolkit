## 适用场景

- 任何"改完要验证是否真的生效"的任务：脚本、自动化、UI 操作、定时任务、部署
- 任何需要向人类报告"已修复 / 已完成"的场合
- 任何存在"测试环境与故障环境不同"风险的任务

## 不适用场景

- 纯文档撰写、纯信息检索、纯方案讨论（无可执行产物，无"是否生效"问题）
- 人类明确说"先不用验证，快速试一下"的探索性操作（但结论仍不得报告为"已验证"）

## 前置条件

- 能够观察产物：读文件、列目录、查进程/任务状态
- 明确知道本次改动的**预期可观察变化**是什么；说不出来的，先问人类，不要动手

## 核心步骤

### V1 验证条件必须与故障条件一致

在 A 条件下验证通过，**不得**据此声称 B 条件可用。

- 反例（真实发生）：解锁态测出 176KB 截图，宣称"窗口句柄截图不受锁屏影响"→ 次日凌晨锁屏态证伪，6 个 `.screenshot-failed.txt`
- 执行要求：凡涉及特定条件（锁屏 / 无人值守 / 特定权限 / 特定时段）的结论，证据必须来自**该条件下的真实运行产物**
- 无法复现该条件时：结论写"未验证"，不写"应该可以"

### V2 语法检查不是验证

`ast.parse()`、`--dry-run`、import 成功、编译通过、"没报错"——**都不算验证**。

- 反例（真实发生）：`ast.parse()` 通过，但漏掉函数参数名撞车，运行即炸
- 执行要求：验证必须是「执行该代码路径 + 检查真实产物或状态变化」

### V3 调用不抛异常 ≠ 操作成功

接口返回正常**不代表**目标状态真的变了。UI 自动化、远程调用、异步任务尤其如此。

- 执行要求：每次写操作后**重读状态**校验（重读控件树、重读文本、重读文件内容、重查任务状态）

### V4 退出码不可信，以产物为准

- 反例（真实发生）：退出码 0，实际 18 秒即终止，什么都没干成
- 执行要求：判定一轮运行是否成功，必须交叉核对**状态文件 + 产物目录的实际文件清单**；不看退出码，不看程序自报的乐观字段

### V5 半成功也是失败

产物存在 ≠ 产物有效。

- 反例（真实发生）：截图文件 > 10000 bytes、颜色数 > 3，但客户区全黑（只有标题栏有色）——仍属失败
- 执行要求：有效性判据要针对**产物的实际用途**设计，不能只看文件大小、行数、是否非空这类属性

### V6 未执行过的分支必须单独标注「未验证」

不得混入"已验证"，不得因为"代码看起来对"就计入。

- 反例（真实发生）：某条件分支长期从未真实执行，潜伏缺陷到真实触发才暴露
- 执行要求：报告中「未验证项」为**独立小节**，宁可列多不可漏

### V7 不凭记忆回答状态问题

"上次跑的结果是什么""那个文件还在不在""任务注册成功没"——一律**先去盘上查**。

- 执行要求：读日志、读状态文件、列目录、查任务信息，拿到实际输出再回答

### V8 改动前先读现状

任何修改前先读当前文件的实际内容，不依据文档快照或记忆中的结构动手。**文档可能滞后于盘上代码。**

### V9 只有两种结论表述

禁止"应该可以""理论上""大概率""基本没问题"。只许两种：

- **「已验证：<证据路径或实际输出>」**
- **「未验证」**

未拿到产物证据前，不得报告"已修复""已完成"。

### V10 最小路径优先

验证或实现任何东西，都走**能达成目标的最小路径**。

- 验证一个能力，就只验证这个能力，不搭完整流程
- 实现一个功能，先跑通最小可用版本，不预先泛化
- 反例（真实发生）：为验证"锁屏能否截图"而去跑完整的四节点流程
- 执行要求：动手前先问"要证明这一件事，最少需要做什么"

### V11 模块化推进，跑通即封存

流程按模块切分，**一个模块验证通过就算通过**，立刻推进下一个，不回头重跑。

- 已跑通的模块不因后续模块失败而重测（除非改动触及它）
- 只在**最后一次全量验证**时完整跑一遍
- 执行要求：每个模块要有明确的「通过判据」和「证据产物路径」，通过后记入进度文件

### V12 失败要如实说，并交出裁决权

方案在真实条件下失败时，立即告知，不重复承诺，不自行加码尝试。
列出候选方向 + 各自代价，交人类裁决，不承诺时间。

（与 `collaboration.md` §人机接口 的失败上限规则配合：达到预算上限必须停）

见 `../observations.md` O008：来源类结论应先给 `codesign` / `spctl` / Team ID 证据。O008 固化前本编号**保留不占用**。

### V14 依赖或宿主换代后，先复跑既有验收，再复核常驻改动

换了宿主版本、依赖大版本、运行环境（应用重装/改名/换端口）之后，**不得假设旧结论仍然成立**。

- 反例（真实发生，2026-09-26）：宿主由 `DSH Desktop.app` 换成 `DeepSeek Harness.app`、端口从 43120 变为 19387；此前为「窗口连不上」装的 3080 端口转发垫片随之失效、为探针写的 `~/.curlrc` 变成冗余，而**系统不会报任何错**——是主动复跑校验 + 逐项复核常驻改动才发现的。
- 执行要求：① 复跑既有验收套件；② 列出自己在该机器上留下的**常驻改动**（后台服务、环境变量、全局配置文件），逐项确认是否仍需要、是否已失效。
- 判据：换代后的报告里必须出现「常驻改动复核」小节，逐项写 **仍有效 / 已失效待撤 / 已撤**。

### V15 跨端协作的验收判据是「对端终态」，不是「我发出去了」

两方及以上协作（跨 harness、AI-AI、人机）时，本端落盘或发送成功**不构成**验收通过。

- 反例（真实发生，2026-09-26）：协作桥修复后本端文件已是 `delivered`，但对端尚未回写 `received`；此前另有 3 条消息停在 `delivery-failed`。只有对端状态机写入终态，闭环才成立。
- 执行要求：验收清单里写明**对端终态字段名**；本端状态只能算中间证据。多轮消息要对**每一条**核对终态，不能只核对最后一条。

## 已知坑

- 现象：验证脚本自己写、自己跑、自己判 PASS，但判据设计得过松
  原因：判据从"文件属性"出发，而非从"产物用途"出发
  应对：写判据前先问"这个产物是给谁用的、用来干什么"，按用途设计判据（见 V5）

- 现象：改完代码后凭印象报告"已接入"，实际入口没改
  原因：文档与盘上代码不同步，凭文档动手（见 V8）
  应对：改动前 `read_file` 实际内容；改动后重读确认

- 现象：一个条件分支永远进不去，导致其中的缺陷长期潜伏
  原因：该分支依赖罕见的外部条件（有新版本、磁盘满、网络断）
  应对：按 V6 单列"未验证"，并在条件自然出现时**补验**并更新记录

- 现象：为验证一个小点，反复占用人类配合（锁屏、重启、提供权限）
  原因：验证项零散，没有合并
  应对：所有需要人类配合的验证项**合并成一次执行**，一次拿全证据

## 验收要点

本技能自身不产出产物。使用本技能的任务，其验收应满足：

- [ ] 每条"已验证"结论都附有**证据路径**或实际输出片段
- [ ] 存在独立的「未验证项」小节（无未验证项时明写"无"）
- [ ] 验证的执行条件与真实故障条件一致；不一致的已标注
- [ ] 判据针对产物用途设计，不是仅检查文件存在/非空
- [ ] 报告中不含"应该可以""理论上""大概率"
- [ ] 换代后已复跑既有验收，并有「常驻改动复核」小节（见 V14）
- [ ] 跨端协作的验收判据写的是对端终态字段，不是本端发送成功（见 V15）

## 术语

- **产物证据**：能被第三方复查的实际输出——文件路径、日志片段、命令返回值、状态文件字段。口头描述不算。
- **故障条件**：缺陷实际发生时的环境条件（时段、登录态、权限、网络、负载）。
- **判据**：判定一项验证 PASS / FAIL 的客观标准，须可由他人独立复核。
